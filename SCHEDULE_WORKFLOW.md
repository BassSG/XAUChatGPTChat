## Version 4: preserve observations and finish a useful decision

Follow this section before preparing prose or artwork. New scheduled publications use `schemaVersion: 4` with the additive desk contract; schema 3 remains accepted for compatibility; historical reports stay readable without changing their claims.

1. Read the latest published report and pending journal IDs. Create a private observations JSON in the temporary directory. Each content version is stored immutably under `../../outputs/analysis-evidence/`, outside the public repository. This checkpoint does not require a finished report or image.
2. Establish or carry the verified W1/D1/H4/H1 baseline under the V4 contract first. Then prefer a compact set of relevant completed bars: recent H1 swings, overhead resistance / underlying support and Critical levels, the chosen M15 setup confirmation, and the subsequent M5 sequence. Aim to read at least 3 H1, 4 M15 and 6 M5 bars when readily available; these counts are a collection target, not a guarantee of structural validity. Expand only to establish an actual swing or prior-plan sequence. Use the direct Data Window and confirmed candle times. If retrieval stalls, make one focused retry, keep verified observations, list the gap, and finish the report. Do not spend the run repeatedly retrying the same UI failure.
3. Evaluate an existing confirmed swing for Stop and an observed opposing level for TP before deciding that a future retest swing is necessary. A complete, cost-adjusted conditional WATCH plan may be published after M15 setup confirmation while its M5 trigger is pending. It must have a defensible entry zone, observed structural Stop, observed target, explicit trigger/invalidation, current spread/news checks, and estimated net R. Never force a WATCH, move a Stop just to achieve an R threshold, invent a future swing, or treat indicator availability as mandatory when primary evidence is sufficient. If the chosen setup genuinely requires a new swing, keep WAIT and name that exact missing structure.
4. Set `decision:{reason,missing:[...],nextAction:"..."}`. Use `DATA_MISSING` for missing primary evidence/calendar, `SIGNAL_PENDING` for verified inputs but no confirmation, `STRUCTURE_PENDING` when Stop/target/entry geometry is still unverified, `NEWS_RISK` for an identified news restriction, `MARKET_CLOSED` for an observed closure, or `CONDITIONAL_PLAN` for WATCH. `missing` lists concrete absent inputs or structure, not generic unavailable wording; WATCH has an empty list. `nextAction` states one visible next event and its timeframe. Put the same distinction in the Thai summary, body and image banner. A data failure must never be described as evidence that the market has no signal.
5. Prepare the UTF-8 report, then run `node scripts/record-analysis-evidence.mjs --input <observations.json> --report <report.json>` BEFORE rendering the PNG. This attaches `evidenceArchive` with the saved content hash, observation time, method and frame counts. The local publisher checks exact quote/OHLC values against this archive and checks that any claimed observed break actually closed beyond its level. A hash proves file integrity, not independent market accuracy; retain original visible evidence/screenshots privately when available, and never fabricate observations to satisfy validation.
6. Finish the report and image early enough to publish within the 15-minute freshness gate. Check that a prior plan is linked to the actual published snapshot, then update the journal and publish. The publisher archives the full report JSON alongside the image, so future review has the original rules and levels. Successful Git push alone is not completion: check the Pages job and Worker latest snapshot. Record the publication result in the journal. If quota/tool access fails, preserve available observations/draft and report the interruption if the runtime permits; do not promise a report was published. The app can identify a missing scheduled report after a 30-minute grace period but cannot infer its cause.
